# 项目看板设计（2026-11）

状态：第一版已实施（2026-11-12）；**第二版重构已实施（2026-11-17），见文末第十节**，第十节与前文冲突处以第十节为准。

## 一、要解决的问题

用户同时推进多个项目，而且是每个项目唯一的推动者，一件事被忽视就会长期搁置。他每天都会主动去看，但看的时候会陷进混乱的信息池。原因是信息没有分层：项目、事项、会话、遗留小项、讨论记录都堆在同一层；各项目主脑又用各自的格式写长文；每看一次，用户都要自己拼出“这是哪个项目的哪件事、现在什么状态、轮到谁动”。

清理会话解决不了问题：很多会话是刻意保留的，而且清掉还会再长出来。要改的是用户和主脑之间交接信息的方式。

## 二、设计原则

1. **注意力的单位是项目，不是单件待办。** 在项目之间切换有衔接成本：进入一个项目，要先把它的背景重新装进脑子，然后才处理得了第一件事；越需要权衡的事，装得越久。同一项目里的 3 件事，远比散在 3 个项目里的 3 件事省力。所以：
   - 看板一级结构是项目；
   - 不做跨项目按时间或紧急程度堆叠的待办清单；
   - 处理也按项目批量进行。
2. **只做提醒和查看，不做输入。** 看板上不写批注、不改状态。要动作时进该项目的主脑会话，一次处理完本项目所有等你的事。
3. **不推送。** 用户会自己来看。提醒靠打开看板时的醒目程度。
4. **位置固定。** 项目在总览里按登记顺序固定排列，不按紧急程度重排，方便用户凭位置记忆找项目。
5. **主脑写卡片，不写长文。** 主脑在对话里的汇报，改成更新卡片，再加一句“已更新卡片 X”。

## 三、结构

### 1. 第一层：项目总览

每个项目一块，内容如下：

| 行 | 内容 |
|---|---|
| 标题 | 项目名、当前阶段 |
| 进度 | 阶段目标进度条（完成、待验收、其余三段），以及“阶段目标 X/Y 完成” |
| 统计 | 进行中、待验收、待办件数 |
| 等你 | 拆成“拍板 N”和“动手 M”，另列等外部件数。拍板要整块时间，动手的事碎片时间就能做 |
| 动静 | 距你上次来看多久；主脑多少天没动（满 5 天标红，用来发现被整个遗忘的项目） |

总览底部有一个收起的小角落：“纯动手的事”，按项目分组列出。纯动手的事（登录下载、点一下设置、发一封拟好的邮件）几乎不用装载项目背景，攒在一起做不吃亏。拍板类的事一律不跨项目汇总。

### 2. 第二层：单项目看板

| 部分 | 内容 |
|---|---|
| 头部 | 阶段与阶段目标、进度条、各列件数、等你拍板和动手的件数、距上次来看多久、主脑动静 |
| 入口 | 项目头部的“进入主脑会话”链接；每张卡片底部的“带去主脑”按钮（见下） |
| 列 | 待办、进行中、待验收、已完成；冻结收起 |
| 排序 | 按主脑排定的优先级；同一优先级里，等你的排前面。不按时间排 |
| 遗留小项 | 在待办列底部合成一行“遗留小项 N 件”，不逐条上板 |

### 3. 卡片

**标签**（第一行）：
- 等你拍板（红）、等你动手（橙）、等外部（灰）；
- 优先级；
- 类型：功能、缺陷、调研、决策、事务；
- ◆ 阶段目标。

**正文**：标题、一句话现状、“要你：……”（只在等你时出现）、“阻塞：……”。

**角注**：在这一列待了几天。

卡片本身不可点，没有按钮。

### 4. 进入主脑会话时的第一屏

切换的成本主要花在“想起这个项目现在在哪”。所以用户从看板进入主脑会话时，主脑第一屏先用三五句帮他重新装上背景，再列本项目所有等他的事：

1. 现在在哪个阶段，离阶段目标还差什么；
2. 距他上次来，完成了什么、新冒出什么；
3. 等他的事：拍板类每项附完整决策栏，动手类每项一行。

这一条写进主脑技能。

## 四、数据

### 1. 卡片文件

每个项目一份，放在台账旁边：`<项目文档目录>/brain/cards.json`。只有本项目主脑写它，随台账一起提交。一个文件只有一个写入者，不会互相覆盖。

文件顶层字段：

- 项目名；
- 阶段、阶段目标；
- 主脑会话名和编号：主脑开局登记自己时写入；
- 遗留小项件数；
- 卡片列表。

卡片字段：

| 字段 | 写法 | 必填 |
|---|---|---|
| 标题 | 20 字以内，业务语言 | 是 |
| 列 | 待办、进行中、待验收、已完成、冻结 | 是 |
| 类型 | 功能、缺陷、调研、决策、事务 | 是 |
| 优先级 | 1 到 3 | 待办、进行中必填 |
| 属于阶段目标 | 是或否 | 是 |
| 球在谁 | 用户、外部、主脑 | 是 |
| 要你 | 一个动作，动词开头，40 字以内 | 球在用户时必填 |
| 拍板还是动手 | 二选一 | 球在用户时必填 |
| 现状 | 一句话，40 字以内 | 是 |
| 阻塞 | 卡在哪件事上 | 否 |
| 进入本列日期 | 每次换列时更新 | 是 |
| 完成日期 | 进已完成列时写 | 已完成必填 |
| 详情 | 拍板类的完整决策栏；主脑自用的分支、提交、验收要点 | 否，看板不显示 |

已完成的卡保留到阶段目标关闭，用来算进度；阶段关闭后由主脑删掉，历史看周流水。

### 2. 登记表

本机 `~/.claude/board/projects.json`，按显示顺序列出每个项目的卡片文件路径。登记表只在本机，不进任何仓库。

### 3. 阶段目标

每个项目由主脑提出一个当前阶段目标，用户确认后，把相关卡片标成属于阶段目标，进度按这些卡算。

还没有阶段目标的项目，看板显示“还没有阶段目标：由主脑提出，你确认后才有进度”。

## 五、和台账的关系

卡片取代台账里的三节：在飞、待用户拍板、队列。队列里的正式待办转成待办卡；遗留小项留在台账，只把件数报给看板。台账只保留规则、遗留小项、环境与待清理；决定、周流水、交接三份文件不变。

## 六、实现

### 1. 看板改造

- 桌面版改造，挂在对话旁边。源码在本仓库插件的 `hooks/register.tsx`，不含任何项目数据。
- 安装：把改造目录写进全局设置的插件目录变量，任何会话里都能用 `/board` 打开。用户固定一个“看板”会话常开。
- 每 5 秒检查卡片文件和台账有没有变化。
- 交互只有四种：
  - 点项目块底部的“进入项目”按钮；
  - 返回总览；
  - 点“进入主脑会话”；
  - 点卡片的“带去主脑”：把这张卡整理成一段话（项目、卡片编号、标题、状态、现状、等你的事、阻塞，末尾留“我的指示：”）放进剪贴板，再跳到该项目的主脑会话，用户按 ⌘V 粘贴、补一句指示即可，不用重打任务描述。
    - 为什么走剪贴板：插件只能往自己所在会话的输入框填字；会话管理接口只给桌面版的会话编号，主脑那边认不出“这是发给我的”，自动填写做不可靠。
    - 复制用系统的 `pbcopy`，必须带 `LANG=en_US.UTF-8`：不带时中文会被悄悄丢掉（退出码 0，剪贴板为空，2026-11-14 实测）。

“距你上次来看”由看板自己记：用户点进项目时，记下时间，存在跨会话存储里。

### 2. 视觉规范

**响应式**：按网页前端的常规做法，用相对宽度和断点，宽度不够时绝不把卡片拉成通栏长条。

| 位置 | 规则 |
|---|---|
| 总览的项目块 | 每块最小 36 格宽；每行放得下几块就放几块，最多 3 块；宽度按百分比均分 |
| 单项目看板的列 | 每列最小 30 格宽；放得下 4 列就一行排开，放得下 2 到 3 列就折行成网格 |
| 窄到只放得下 1 列 | 顶部出现“待办 9 / 进行中 2 / 待验收 3 / 已完成 1”分段切换，一次只看一列，和手机上的看板产品一样 |
| 卡片 | 宽度跟随所在的列。卡片是块，不是字条：内容自上而下分区，不把信息从左到右串成一行 |

**块的版式**：

- 项目块，自上而下：
  1. 标题行：项目名，右侧是阶段标签；
  2. 阶段目标一句话；
  3. 进度条，下面一行小字“阶段目标 X/Y 完成”；
  4. 统计块：大号数字加小字说明，进行中、待验收、待办三块横排；
  5. 等你：拍板、动手、等外部各一个色块；
  6. 角注：主脑动静、距上次来看；
  7. 底部右侧“进入项目”按钮。
- 事项卡片，自上而下：
  1. 标签组；
  2. 标题；
  3. 现状；
  4. “要你”小区块：浅红或浅橙底，小标题加一句话；
  5. “阻塞”小区块：浅红底；
  6. 角注：在这一列几天。
- 标签是独立色块，放在可折行的横排里，窄了自动换行。

**点击**：按钮是按钮，块是块。桌面版改造的元素表里只有按钮能点，而按钮里只能放文字，把整块塞进按钮就会把内容挤成一行。所以块只负责展示，悬停时边框变蓝、底色微亮；进入靠块底部的按钮。

**配色**：

| 用途 | 样式 | 颜色 |
|---|---|---|
| 等你拍板 | 实心色块，白字 | 红 |
| 等你动手 | 实心色块，白字 | 橙 |
| 等外部 | 实心色块，白字 | 灰 |
| 主脑多天没动 | 实心色块，白字 | 红 |
| 优先级 P1、P2、P3 | 浅底色块，彩字 | 红、琥珀、灰 |
| 类型：功能、缺陷、调研、决策、事务 | 浅底色块，彩字 | 蓝、粉、青蓝、琥珀、灰 |
| 阶段、阶段目标 | 浅底色块，彩字 | 青 |
| 列：待办、进行中、待验收、已完成 | 列头色点，列底浅色衬底 | 紫、蓝、琥珀、绿。待办用高亮的紫色，因为它是用户进项目后最先看的列 |
| 进度条 | 三段 | 绿（完成）、琥珀（待验收）、灰（其余） |
| 卡片边框 | 等你的卡用对应颜色描边 | 红或橙 |

“球在谁”用实心色块，因为它是用户最先要找的信息；其他标签用浅底，不和它抢注意力。

### 3. 格式检查（强制，不靠主脑自觉）

- 检查脚本放在本仓库 `board/check-cards.py`，检查列名、必填项、字数、日期格式。
- 主脑写完卡片文件后，由钩子自动运行检查；不合格就把错误退回给主脑，要求它改。
- 看板读到不合格的文件，项目块显示红框，写明原因，不静默跳过。

### 4. 主脑技能改动

- 台账模板删掉在飞、待拍板、队列三节，改成卡片文件模板。
- 原来“每个动作后改台账”的触发点，改成“改卡片”。
- 给用户的回复缩短：先写“已更新卡片 X”，后面只接需要用户此刻在对话里回答的问题。
- 新增“用户从看板进来时的第一屏”（第三节第 4 条）。
- 新增“提出阶段目标”：没有阶段目标的项目，主脑提出一个，交用户确认。
- 迁移步骤：主脑下次被唤醒时，自己把台账三节转成卡片，交给检查脚本验证，然后提交。

### 5. 已核实与待核实

## 十、第二版重构（2026-11-17）

### 1. 为什么重构

第一版用了一周，盘点到的问题都指向同一个根子：卡片是主脑**手写的快照**，看不到历史，也看不到会话的真实状态。

1. 一个项目的卡片文件一周被手改提交 78 次；进入本列的日期、完成日期、打回次数都靠主脑记得改，规矩全写在技能里。
2. 有的“进行中”卡挂了二三十天，看板分不清是有会话在干活还是早停了。
3. 一个分支会话弹出权限确认、停了很久，看板完全没反映，用户被确认弹窗烦到才发现。
4. 已完成的卡在阶段关闭时删掉，历史只能靠台账周流水，两处记同一件事。
5. 信任指标（`2026-11-trust.md`）只能靠主脑每次打回时记得加一，是补丁。

### 2. 三块改动

1. **卡片改为“命令记事件、自动算状态”**（`board/card.py`，说明见 `board/cards-format.md`）。`events.jsonl` 只追加，是唯一的事实来源；`cards.json` 由命令生成。规则由命令检查，违规的不生效；手改两份文件会被钩子拦下。历史永久保留，信任指标按近 7 天和本阶段自动算，周流水用 `card log` 生成。做法参考事件溯源。
2. **会话实况**（`board/live.sh`）。插件在每个会话挂轻量钩子：发消息、工具调用完成记“在跑”，弹出权限请求记“等你批准”，一轮结束记“空闲”，出错记“出错”，会话结束删文件。靠桌面版设给每个会话的会话编号认人；卡片用 `sessions` 字段记对应会话。看板在卡片上显示会话状态，进行中的卡会话停了 3 小时以上算停滞。
   - 实测（2026-11-17）：真实会话里，工具调用期间状态为“在跑”；需要权限时变为“等你批准”，之后回到“在跑”；会话结束文件删除。
   - 这个钩子每次工具调用都会跑，用 sh 写、不解析输入、不经统一记录包装器（包装器要起 Python，开销不值）；失败静默，看板显示“会话不在线”而不是错的状态。
3. **第一屏改为“现在要我做的”**。只列有事等用户的项目，**按项目分组、项目按登记顺序固定**；组里依次是等你批准的会话、等你拍板、等你动手、带验证产物的新交付。下面是全部项目块，加了会话实况和信任指标。
   - 分组而不平铺，是为了守住第二节原则 1（注意力的单位是项目）：用户 2026-11-11 驳回过跨项目按等待时间平铺的待办清单。第二版改的是“第一屏只放要你做的事”，一级单位仍是项目。
   - “带去主脑”升级：看板把卡片内容写到 `~/.claude/board/pending/<主脑会话编号>.json`，主脑会话里的本插件每 2 秒看一次，读到就填进输入框（剪贴板留一份兜底）。第一版只能复制、到了主脑按 ⌘V。
   - 新交付带“看验证产物”按钮，打开主脑合入时记下的产物目录。

### 3. 迁移

各项目主脑执行一次 `card import`，把手写的 `cards.json` 导入成事件；`detail` 里记的会话编号改用 `link` 记；看板登记表补 `root`。步骤见主脑技能「迁移到卡片命令」。三个已迁移项目的真实卡片已在临时目录试导入，件数和字段一致。

## 十一、首屏分级（2026-11-20）

### 1. 问题

第二版上线三天，登记到 6 个项目，首屏约 37 件：等你拍板或动手 17 件，“新交付” 20 件。两处设计缺陷：

1. **新交付判定太宽，又没有出口**。凡是“已完成、填了产物、3 天内”都算。主脑把产物栏当成“证据写在哪”，提交号、周流水、决策文档都填了进去；20 件里真有录屏截图可看的只有 3 件。用户看过了也不会消失，只能等过期。
2. **首屏没有分级**。上半按项目分组列待办，每件一张大卡；下半再把全部项目块摆一遍，信息重复。一个项目一天合入 10 件，首屏就成了长瀑布。

### 2. 改法

1. **首屏合成一张项目清单，三级**：项目行（阶段、要你做的事各几件、会话在跑或停滞）→ 展开前 3 件（有等你批准或拍板的项目自动展开，其余收起，“还有 N 件”可全部展开）→ 项目页。原来的项目块去掉，信任指标只在项目页。
2. **“待你看”由主脑明确交出**：`card done --review`（或事后 `card review`），只给有录屏截图、用户能看到变化的事。看板上“看过了”只记在本机插件存储（用户 2026-11-20 选定），不写项目仓库：保住“只有主脑写卡片”的规矩，代价是主脑和信任指标看不到用户验收过。完成 7 天后自动下架。
3. **产物栏收紧**：`done --evidence` 时命令检查路径存在（绝对路径或相对仓库根目录）。已有的卡不追溯。
4. **项目页已完成列**：按完成日期从新到旧，先显示 5 件。

仍守第二节原则 1：一级单位是项目，项目按登记顺序固定，不按紧急程度重排（展开与否随紧急程度变，位置不变）。

## 十二、决策卡审批状态（2026-11-24）

### 1. 需求

用户原话：“能做类似标签分类么？哪些定了哪些没定？或者分栏目区分也可以”；“不要叫等用户，就叫待审比较好”；“和常规 oa 一样，待审，通过，否决”。

决策卡原来只有“球在谁”：用户答复后球回到主脑，卡结案或挂着，看板上看不出这件事最后是通过还是否决；已完成的卡 14 天后下架，以前定过什么也查不到。

### 2. 做法

1. **审批状态三值**：待审、通过、否决，只给决策卡。存在卡片的 `approval` 字段，由事件算出：
   - 通过、否决由两条新命令记事件：`card approve <编号> [--note 用户原话]`、`card veto <编号> --reason 原因`。两者都把卡结案（移到已完成，球回主脑），记下审批日期；否决原因必填。被否决的卡不删。
   - 没记过结论的决策卡：没完成就算待审，已完成的不标。新建的决策卡因此默认待审；旧事件不带审批状态，重放结果一样，不用迁移。
   - 待审的决策卡不能用 `done` 结案，逼主脑记下结论；作废仍用 `drop`。否决后要重新提审：`move` 回待办，再 `ask --decide`，回到待审。
2. **看板**：卡片上加审批色块（待审红色实心、通过绿色、否决灰色），通过、否决的卡显示结论和依据。项目页加一排“审批”按钮，可只看待审、通过或否决的卡，按组摆开。首屏项目行的“等你拍板 N”改为“待审 N”：球在用户、要拍板的卡，加上没完成的决策卡（冻结的不算）。
3. **审批记录不下架**：已完成、审批过的决策卡过了上板期限，移到 `cards.json` 的 `decided` 列表，不进分列看板，按“通过”“否决”筛选时照样列出。
4. **改名**：给用户看的“等用户”“等你拍板”一律叫“待审”（`card show` 的标记、看板色块、首屏计数、“带去主脑”的文字）。动手类仍叫“等你动手”，那不是审批；“会话等你批准”说的是权限弹窗，不改。

### 3. 兼容

6 个已登记项目的事件在副本上用新命令重放、检查全部合格；小说项目 12 张没完成的决策卡（D-35～D-42 和 4 张冻结的）算待审，其余项目原样。旧版命令生成的 `cards.json` 没有 `approval` 字段，看板按同一规则自己补算，主脑不用先跑命令。
