# 信任：用户不在场时，凭什么相信 AI 做对了（2026-11，草案第二版）

依据：Lauren Tan 2026-11 演讲《All Code Is Slop (Except Mine)》、她 2026-09 的直播、她的 pstack 插件目录；本仓库治理设计 `2026-11-governance.md`；对各项目验收现状和文字规则的盘点。

## 一、要回答的问题

用户不读代码，验收靠主脑给的证据。现在这道关的样子：

- 主脑验收已经很硬：全量测试、自选变异探针（故意改坏代码，看测试会不会变红）、核对提交。这些属于“代码层”的证明。
- 缺的是“应用层”的证明：没有一个可重复的办法，证明“用户实际点开时它是对的”。交给用户的仍然是文字结论。
- 没有质量数字。现有的三个注意力指标量的是打扰了用户多少次，不是交付质量。
- 大量约束仍是文字：全局规则、主脑技能、项目规则、项目记忆。文字会被跳过，也会被智能体“矫枉过正”，把一次纠正当成铁律到处套用。

## 二、借用的框架：约束从强到弱四层

1. 代码与架构：让错误写不出来。
2. 静态检查和测试：类型、代码规范检查、依赖检查、测试、持续集成。
3. 运行验证：真实启动应用、真实操作、留下产物。
4. 文字规则：只放判断不了、写不成检查的东西。

每次纠正，先问“能不能落到 1、2 层”，不行再考虑 3，最后才写成文字。我们的流程层（钩子、回报检查、卡片检查）已经按这个思路做了；项目代码层还没做。

## 三、三条工作线

### 线一：验证产物（第 3 层，最优先）

每个有界面或服务的项目，建一个**验证技能**，放在项目仓库里，由项目主脑派分支建、亲手验收。它包含三部分：

| 部分 | 内容 |
|---|---|
| 可复现脚本 | 一条命令启动应用、走指定流程、存下录屏、截图、关键接口返回。网页用浏览器自动化，服务端用集成冒烟。脚本固定下来，不让每个会话临场发挥 |
| 功能地图 | 一份清单，每个功能写：用户怎么叫它、入口在哪、关键元素、怎么验证。按用户的叫法写，这样用户说“侧边栏那个”，智能体不用猜 |
| 产物约定 | 产物放项目本地、不进版本库的目录，按卡片编号分开；回报里写路径和复现命令 |

验收流程的变化：

1. 派活模板的回报格式加「验证产物」一栏：路径和复现命令。功能类、缺陷类的卡，这一栏不能空。回报格式检查钩子强制执行。
2. 主脑验收加一步：亲手重跑验证脚本，产物和回报一致才往下走。
3. 主脑交给用户验收时，发录屏和截图，不发“已验证通过”这句话。
4. 改了功能入口却没更新功能地图的，打回。先靠主脑看，等稳定了再写成检查脚本。

第二步（试点稳定后）：复杂流程在开工前先出一张状态流转图，请用户确认意图，再实施。图比文字更容易看出“它理解偏了”。

不适用：纯文档、纯测算类的项目没有应用可点。它们的“验证”是固定随机种子后重跑，结果和报告里的数字一致。

### 线二：信任指标（给出一个数）

在现有注意力指标之外，加两个质量数，按阶段统计（已完成的卡在阶段关闭时才删，正好对齐）：

1. **打回率**：本阶段打回次数 ÷ 本阶段已完成件数。卡片加 `rejects` 字段，主脑每打回一次加一。
2. **返工数**：合入后才发现的问题。缺陷卡加 `causedBy` 字段，指向引入它的那张卡。

看板在每个项目上显示这两个数；卡片检查脚本校验新字段。主脑周汇总写进 handoff。

不选“回滚率”：我们的项目合入量小，回滚极少，这个数太稀疏，说明不了问题。

### 线三：文字规则下沉（第 1、2 层）

对全局规则、主脑技能、派活模板、各项目规则和项目记忆，逐条分成四类：

| 类别 | 处理 |
|---|---|
| 能写成检查的工程规矩（比如“改了迁移必须重新生成代码”“某类查询必须按某字段排序”） | 在项目仓库里写成检查规则或测试；报错信息写清为什么错、正确修法；**同时清掉库里已有的违规**；然后删掉那条文字 |
| 和全局规则或主脑技能重复的协作偏好 | 删掉，只留一处 |
| 领域事实（外部接口的真实行为等） | 留在记忆或项目文档；能写成契约测试的写成测试 |
| 需要判断的偏好 | 留作文字 |

做法：逐条分类是机械活，派便宜模型做初分，主脑复核；涉及删除用户纠正过的记忆，先列清单给用户过目（记忆目录有私有版本管理，可恢复）。落检查的部分按项目派分支，一个项目一个批次。

不照搬的：她禁掉绝大多数代码注释、禁掉某些框架接口，是针对她的代码库得出的结论。我们按项目在审计中出现的真实问题决定，不预设。

## 四、暂缓

- 形式化验证、基于属性的测试：涉及钱的状态流转值得做，等线一稳定后单独立项。
- 自动开工（接报警、群消息拉起智能体）、多路并行尝试、多模型互相挑错：前几层没打牢时只会放大垃圾。

## 五、顺序与验收

| 阶段 | 内容 | 谁做 | 算完成 |
|---|---|---|---|
| 1 | 本仓库：回报格式加验证产物栏和检查、主脑技能验收步骤、卡片新字段、看板显示两个数 | 本仓库会话 | 用例和官方校验通过，新会话实测 |
| 1 | 试点项目建验证技能和功能地图 | 试点项目主脑派分支 | 主脑亲手跑通；用户看过一次录屏验收 |
| 2 | 试点项目文字规则审计和下沉 | 试点项目主脑 | 分类清单经用户过目；检查规则合入；对应文字删除 |
| 2 | 其余有界面的项目建验证技能 | 各项目主脑 | 同上 |
| 3 | 其余项目审计；状态流转图；涉及钱的属性测试 | 各项目主脑 | 单独立项 |

两周后复盘：试点项目里功能类、缺陷类卡片有多少带了产物；用户验收一件事平均花多久；打回率和返工数；删了多少条文字、加了多少条检查。

## 六、代价

验证会变贵：每件事多一次启动应用、录屏、复跑。她的经验是大约七成的消耗花在验证上。我们会明显低于这个比例，但单件成本和时长会上升。换来的是用户验收从“读文字、凭感觉”变成“看录屏”，并且有一个数说明质量走向。
