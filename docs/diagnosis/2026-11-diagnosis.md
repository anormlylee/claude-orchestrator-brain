# 开发流程诊断与重组方案（2026-11）

数据范围：2026-10-01 至 11-09，lee 亲手发出的 1152 条消息（其中 274 条在反映问题）+ 177 条协作流程类反馈记忆。主题明细与逐条依据含 lee 原话，不进本仓库（仓库公开），存于本机 `~/.claude/diagnosis/2026-11/`；抽取脚本见 `scripts/`。

做法：脚本从 5.5GB 会话记录里筛出 lee 原话（零模型成本）→ 便宜模型逐条打标（抽检准确）→ 中档模型聚成 18 个主题并对照每条规则的立规日期 → 本文做综合判断。

## 一、结论

1. **“少断点”和“不走偏”不矛盾，数据也支持这一点。** 走偏的上涨几乎全部发生在开工和方案阶段（11 月上半月走偏 55 条里有 43 条），执行中越权、交付没验证这两类反而在下降。所以控制走偏靠的是开工那一道关，而不是执行中多问。
2. **断点里，“推给 lee 手动做”在下降，“无意义授权”纹丝不动。** 前者靠第 11、12 条规则压下来了（每百条消息从 4.8 条降到 0.3 条）；后者的根因在权限配置层：放行名单只有 12 条，新会话的默认权限模式是每步都问。文字规则管不到这一层。
3. **只有被钩子强制执行的规则被证明有效。** 中文回复检查钩子装上之后，夹英文的问题 26 天零复发；其余对策基本是纯文字规则或单个项目的记忆。
4. **项目记忆无法跨项目生效。** 同一个要求（优先复用和开源、测试环境安全从简、不要逐步确认）在不同项目里各说了至少 3 遍，换一个项目又要重说一遍。
5. **规则之间已经互相打架。** 第 10、11、12 条对红线的口径各不相同；第 5 条（测试数据删除也要确认）、第 6 条（阶段结束提醒、合并前确认）已经被至少 5 个项目的记忆推翻；“Git 提交规则”一节和实际流程脱节。lee 的原话是“按了葫芦起了瓢”。

## 三、重组原则

1. **每条规则都要写明靠什么执行**：钩子、模板里的必填栏，或者权限配置。说不出执行方式的规则，要么改成机制，要么删掉。
2. **分层，每层只放该放的东西**：
   - 全局偏好清单：一页以内，只写 lee 跨项目的工作偏好和红线，取代现在 18KB 的全局规则。
   - 流程仓库：主脑技能、派活模板、回报模板、钩子，规定开工、执行、交付三段怎么走。
   - 权限配置：放行名单、默认权限模式。
   - 项目记忆：只放本项目特有的事实和业务约束，不再放通用工作偏好。
3. **两道关，中间不打断**：
   - **开工对齐关**：派活之前，复述对需求的理解，盘点能复用的已有成果，检索决策台账，列出要查证的外部事实。lee 在这里认真确认一次。
   - **执行段**：不请示，权限放行和钩子负责兜底。
   - **交付验收关**：交付物附上位置、断言附上来源，lee 会打开的东西必须先自检过。
4. **先试点，再推广**：先在一个项目里跑一周，拿同样的脚本重测指标，再推到所有项目。

第二批插入项：决策路由（2026-11-10 完成）。

- **起因**：某项目主脑把两项“上链后改不了”的技术设计交给 lee 拍板。推荐的依据，一是拿 lee 说过的一句原则去否定一个外部参照方案，二是拿外部方案的做法当证据；用来查清这两项关键事实的调研还在排队；选项只有两个。lee 驳回：他的话和外部方案都不是标准答案，分析要从客观事实和核心需求出发。
- **根因**：
  1. 职责表里没有人负责技术判断；
  2. 派活模板写的是“能撤回的自己做掉”，反过来就成了“撤回不了的交给用户”。可逆性本来决定的是谨慎程度，被当成了决定谁来定的依据。
- **改动**：
  1. 主脑职责从四件改为五件，加上技术裁决；
  2. 新增「决策路由」：先拆题，技术部分主脑凭证据裁决（撤回不了的提高证据门槛），只把价值取舍交给 lee，并用业务语言问；
  3. 用户的话先归类（目标、约束、偏好、参照）再用，原话和外部方案只当佐证；
  4. 待决项必须写核心需求、关键事实及其确立状态、至少三个选项，关键事实没确立的不交给 lee；
  5. 回报检查钩子同步检查类型、需求、选项三栏；
  6. 周流水开始记注意力指标（打扰次数、停滞未发现时长、无干预连续通过数），周末汇总进 handoff。

第二批插入项：讨论会话形态（2026-11-11 完成）。

- **起因**：lee 让某项目主脑开一个讨论会话，主脑用派活模板开成了出方案的执行会话；纠偏时又单方面另开了一个新会话。
- **根因**：主脑技能只有派活这一种开会话的方式，讨论被套进任务清单、完工回报、验收要点，必然被做成交付。以前讨论会话都是 lee 自己开，现在开始由主脑代开，技能没跟上。纠偏时的单方面动作，是急于交出东西的同一个习惯，已有的“开工对齐”“不拆碎会话”两条覆盖，不另加条款。
- **改动**：
  1. 主脑技能加「开讨论会话」：用独立的开场提示，不列任务、不写验收；开出后主脑不催、不插话，被它的轮次唤醒时直接结束；
  2. 派活模板加「讨论会话的开场提示」：交过去的是问题、用户原话、已知事实及来源、还没定的事；第一轮只复述问题和给切入点，然后等用户；用户没要求就不派子代理、不做大范围调研；
  3. 台账在飞状态加“讨论中”。
